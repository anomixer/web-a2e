# Desktop build (Tauri v2)

ApplEm ships as a web app and as a native desktop app built with
[Tauri v2](https://v2.tauri.app), the same tool as web-spec's desktop build.
Both run the same frontend (`src/js`) and the same WASM core. There is no
second copy of the emulator: the desktop build is the web app in a native
window, with its header moved into the menu bar.

## Layout

```
src-tauri/
  Cargo.toml
  build.rs
  tauri.conf.json            window, bundle, dev/build wiring
  capabilities/default.json  permissions for the dev window (Vite on :3000)
  capabilities/packaged.json the same, for the packaged app's local origin
  icons/                     generated by scripts/make-app-icon.swift
  src/main.rs                desktop entry point
  src/lib.rs                 plugins, the local server, the window
src/js/platform/
  runtime.js                 isTauri()
  desktop-host.js            html.tauri-host, reworded hints, external links
  native-menu.js             the menu bar
```

## Prerequisites

Rust (`rustup`), Xcode Command Line Tools on macOS, and `npm install`. See
https://v2.tauri.app/start/prerequisites/ for Linux and Windows.

## Running

```bash
npm run tauri:dev     # Vite on :3000 in a native window, JS hot reload
npm run tauri:build   # npm run build, then .app/.dmg into src-tauri/target/release/bundle
npm run tauri:build -- --bundles app   # just the .app
```

### Signed and notarised (macOS)

```bash
npm run desktop:mac                 # sign, notarise, staple: .app and .dmg
NOTARIZE=0 npm run desktop:mac      # sign only, for a quick local check
```

`scripts/build-desktop-mac.sh` finds the Developer ID Application certificate
in the keychain, has Tauri sign with it (hardened runtime, secure timestamp),
submits the `.dmg` to Apple with a stored `notarytool` profile, staples the
ticket to the `.dmg` and the `.app`, and checks both with Gatekeeper. The
profile is `applem-notary` if it exists, otherwise one another app stored for
the same Apple ID (`NOTARY_PROFILE` overrides). The version comes from
`src/js/config/version.js`, so a release bump reaches the app without editing
`tauri.conf.json`.

The build is for the machine's own architecture (`aarch64` here). An Intel or
universal build needs `rustup target add x86_64-apple-darwin` and
`--target universal-apple-darwin`.

The web build is untouched. `vite.config.js` only changes when Tauri runs it:
a fixed port and no browser tab.

## Why the packaged app serves itself on http://localhost:47123

The emulator hands frames and audio across threads in a `SharedArrayBuffer`.
WKWebView reports a page from Tauri's own `tauri://` scheme as cross-origin
isolated when it carries COOP/COEP, and still leaves `SharedArrayBuffer`
undefined; the same page from `http://localhost` gets it. So a release build
serves `dist/` through `tauri-plugin-localhost` with the two headers added,
and the window loads that. Measured in the packaged app: `crossOriginIsolated`
true, `SharedArrayBuffer` a function, and the shared framebuffer in use.

The port is fixed on purpose. It is part of the origin, and localStorage and
IndexedDB (settings, save states, disks) are keyed by origin, so a port chosen
per launch would lose all of them on every restart. Changing `LOCAL_PORT`
has the same effect once. If something else holds the port, the app has
nothing to load.

Only one copy of the app runs (`tauri-plugin-single-instance`, registered
first): two would both claim the port, one on IPv4 and one on IPv6, and the
second window could load the first copy's pages. Opening the app again brings
the running window forward instead.

A page on that origin is a remote URL to Tauri, which is why
`capabilities/packaged.json` exists. Plugin commands (menu, opener, window
title) are allowed there; an app-defined `#[tauri::command]` would also need
permitting before that page could call it.

## The menu bar

The header is hidden (`html.tauri-host header`) and everything it offered is
in the native menu bar: File, Edit, Machine (power, Ctrl+Reset, Reboot, the
machines, a IIgs's memory), View, Debug, Dev (plus the agent when a server is
running), Sound, Window and Help. The header stays in the page because it is
still what runs: every native item clicks the control it stands for, so
handlers, confirmations and stored state are the browser build's own.

`native-menu.js` reads a plain model off the DOM and rebuilds the native menu
only when the model changes, because the header churns (the File trigger
flashes on every autosave) and a rebuild is a hundred or so native calls. It
always rebuilds after a menu action, because macOS flips a check item's tick
itself: choosing the theme already set would otherwise untick it.

A new item in a header dropdown appears in the menu bar with no change here,
as long as it is one of the shapes `readPanel` knows: a button, a button with
`.menu-check-icon`, a row with a `*-btn-group`, or a row with a checkbox.

## ⌘ keys

A browser keeps ⌘Q, ⌘W and the like whatever the page does; WKWebView asks the
page first, and the screen swallows every key it sees. So in the desktop build
`InputHandler` lets a ⌘ combination through to the menu bar when the machine
has no use for it (⌘ is not Open Apple), and always lets ⌘Q through, which
keeps quitting the same as in the browser. With ⌘ as Open Apple (the IIgs
default) every other ⌘ key goes to the machine, and the menu bar's items are
reached with the mouse.

## Icons

Regenerate with `swift scripts/make-app-icon.swift public/assets/applem-logo.png icon.png` and `npm run tauri icon icon.png -- -o src-tauri/icons`,
then delete the `android/`, `ios/` and `Square*`/`StoreLogo` files it adds.
The web app's icons in `public/icons/` come from the same script with `bleed`
as a third argument (a full square, which iOS and Android mask themselves),
resized with `sips -z`.
